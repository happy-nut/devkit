# 이미 있는 수정 검증

열린 PR 이나 머지된 커밋이 보고를 그럴듯하게 고칠 때 이 방식을 쓴다.

이미 있는 산출물이 수정을 갖는다. 검증한다. 그것을 고치거나, 경쟁 패치를 쓰거나, 다른 PR 을 열지 않는다.

## 산출물 자격

구체 산출물 하나가 있어야 한다.

- 증상을 다루는 코드 변경이 있는 열린 PR
- 머지된 PR
- 코드와 의도가 맞는 머지된 커밋

스레드의 주장, 트래커 상태, 브랜치 이름, PR 이나 커밋 없는 원인 가설은 모자라다.

산출물이 여럿이면 출처 스레드나 트래커에서 링크된 것을 고른다. 없으면 영향받는 코드에 가장 가까운 것을 고르고 이유를 쓴다.

## 작업 트리 지키기

저장소가 허락하면 격리된 워크트리(`git worktree`, 또는 `Agent` 의 `isolation: "worktree"`)나 다른 깨끗한 체크아웃을 쓴다. 사용자 변경을 덮어쓰지 않는다. 원격 루틴은 매 실행이 새 클론이라 사용자 변경이 없다.

기록할 것:

- 기준 리비전
- 고친 리비전
- PR 이나 커밋 URL
- 두 실행이 함께 쓰는 빌드와 환경 입력

PR 링크는 보통의 `github.com` 링크를 쓴다.

## 기준 재기

열린 PR 이면 그 base 브랜치가 기준이다.

머지된 수정이면, 수정 바로 전 리비전이 빌드되고 옛 동작을 나타낼 때 그것이 기준이다.

설정된 제어 어댑터로:

1. 기준 앱을 띄운다.
2. 맞는 앱과 환경인지 확인한다.
3. 보고된 경로를 실제 UI 동작으로 돈다.
4. 증상을 가르는 상태를 관찰한다.
5. 되돌리고 다시 한다.
6. 기준 녹화, 스크린샷, 상태 확인을 잡는다.

기준에서 증상이 두 번 나타나지 않으면 기준이 없는 것이다. 수정이 통한다고 주장하지 않는다.

## 고친 빌드 재기

같은 환경과 데이터로 PR 이나 수정 커밋을 빌드해 돌린다.

1. 같은 UI 경로를 돈다.
2. 두 번 반복한다.
3. 깨진 상태가 사라졌는지 확인한다.
4. 기대 상태가 나타나는지 확인한다.
5. 이후 녹화, 스크린샷, 같은 상태 확인을 잡는다.

컴파일이나 시험에서 멈추지 않는다. 이후 결과는 돌고 있는 고친 앱에서 나와야 한다.

## 결과

### 확인됨

기준에서 두 번 재현되고 고친 빌드에서 두 번 해결된다.

- 운영 상태를 검증됨으로 둔다.
- 산출물을 링크한다.
- 출처 사전 확인 뒤 짧은 출처 스레드 답글 하나를 올린다.
- 전후 결과를 넣는다.
- PR 을 열지 않는다.

### 모자란 수정

기준과 고친 빌드 둘 다에서 증상이 나타난다.

- 운영 상태를 재현됐지만 고쳐지지 않음으로 둔다.
- 산출물을 링크하고 증상을 해결하지 못했다고 말한다.
- 이번 실행이 아직 쓰지 않았으면 평소의 재현 확인 출처 갱신을 올린다.
- 경쟁 PR 을 열지 않는다.

### 결론 못 냄

기준이 재현되지 않거나, 고친 앱을 돌릴 수 없거나, 증거가 증상을 가르는 상태를 보여 주지 않는다.

- 성공이라고 하지 않는다.
- 어느 쪽 절반을 잴 수 없었는지 쓴다.
- 결과는 운영 스레드나 실행 출력에 둔다.
- 직접 온 질문에 답해야 하는 경우가 아니면 출처 스레드에 아무것도 올리지 않는다.

## 정리

두 빌드를 멈추고, 임시 프로필과 캡처를 보존 정책대로 지우고, 사용자 작업을 버리지 않고 저장소를 이전 상태로 돌린다.
