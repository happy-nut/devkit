# 기능 지도 HTML

`/dev:verify-setup` 이 만든 기능 지도를 사람이 한눈에 보는 HTML 한 장으로 만든다. 지도는 에이전트가 읽는 글이라 길고, 어디가 비었는지는 글만 봐서는 안 보인다. 이 스킬은 빈 곳을 숫자와 색으로 드러낸다.

결과물은 파일 하나다. 외부 스크립트·글꼴 없이 오프라인으로 열린다. 첫 화면은 왼쪽에서 오른쪽으로 흐르는 그래프다. 왼쪽 열이 진입점 묶음(단축키, CLI 명령, HTTP 라우트, 공개 함수), 가운데 열이 기능, 오른쪽 열이 끝점인 하위 기능이다. 주인 없는 진입점은 기능 열의 「Unowned」 로 흐르고, 하나라도 있으면 머리의 배지가 「MECE 아님」 이 된다. 자동 검증이 없는 노드와 선은 꺼진 것처럼 흐리게(회색, 점선) 그리지만 누르면 똑같이 열린다. 노드를 누르면 그 길이 밝아지고 패널(휴대폰은 아래 시트)에 영어 이름과 복사 단추, 한국어 설명, 판정과 근거가 뜬다. 휴대폰에서는 처음부터 화면 너비에 맞춰 열리고 손가락으로 위아래로 넘겨 본다. 목록·진입점·빈칸 탭도 있다.

## 이름과 설명: 지도가 낱말장이다

기능 지도는 사람과 에이전트의 공통 언어(유비쿼터스 언어)다. 사용자는 HTML 에서 `CMP-3 branch tip` 을 복사해 「CMP-3 branch tip 고쳐」 처럼 그대로 말하고, 어느 스킬의 에이전트든 그 이름으로 지도에서 같은 기능을 찾는다. 그래서 이름과 설명은 scratch 파일이 아니라 저장소의 지도 파일 안에 산다.

- **기능.** H1 이 `# <ID> - <영어 이름>` 이거나 `# <영어 이름>` 이다. 앞의 것이면 그 ID 를, 아니면 파일 이름을 ID 로 쓴다. 파일 이름이 그 파일의 하위 기능 ID 와 같으면 `.md` 까지 붙여 쓴다(`agent-chat.md`). H1 아래 첫 문장이 한국어 설명이다.
- **하위 기능.** `Sub-features` 글머리가 `` - `<ID>` **<영어 이름>**: <한국어 설명> `` 이다.
- **이름은 영어.** 2~4 낱말, 한글 없음. 코드와 지도에 이미 있는 낱말에서 따온다(`branch tip`, `--staged`, `find usages`). 지어낸 이름은 에이전트가 코드에서 찾지 못한다.
- **설명은 한국어.** 사람이 읽는 한 문장. 그 기능이 사용자에게 무엇을 해 주는지 쓴다. 키나 플래그는 원문 그대로 둔다.
- 스크립트가 지도에서 이름과 설명을 읽고, 없거나 틀리면 `naming_problems` 로 센다(「영어 이름이 지도에 없음」, 「한국어 설명이 지도에 없음」, 「이름에 한글」). 키트의 지도 예시도 같은 검사를 거친다.

## 낱말

이 스킬과 HTML 은 이 낱말만 쓴다. 「지도에 든」 같은 말은 쓰지 않는다.

| 낱말 | 뜻 |
|---|---|
| 진입점 | 사용자나 호출자가 기능에 들어오는 문 하나. 단축키, 메뉴 항목, 라우트, CLI 명령, 공개 함수 |
| 주인 기능 | 그 진입점이 여는 화면·처리기를 맡은 기능. 진입점마다 하나 |
| 주인 있음 / 주인 없음 | 주인 기능이 정해졌고 그 파일에 진입점이 적혔다 / 아니다 |
| 제외 | 기능이 아닌 진입점(영역 이름, 닫기 단추). 이유를 단다 |
| 끝점 | 하위 기능. 사용자가 보는 결과 하나 |
| 자동 검증 / 방법만 / 없음 | 끝점을 스크립트·시험이 돌린다 / 손으로 모는 방법만 있다 / 둘 다 없다 |
| MECE | 진입점마다 주인이 정확히 하나(겹침 0)이고, 주인 없음이 0 이다(빠짐 0) |
| README 빈칸 | README 의 `## Not mapped yet` 절에 사람이 적어 둔 아직 안 그린 곳 | 파일 이름이 그 파일의 하위 기능 ID 와 같으면 `.md` 까지 붙여 쓴다(`agent-chat.md`).

## 무엇을 재나

**하위 기능 커버리지.** 기능 파일 `Sub-features` 절의 글머리마다 맨 앞 `` `ID` `` 를 하위 기능 ID 로 읽고 셋 중 하나로 가른다.

| 판정 | 조건 |
|---|---|
| 자동 검증 | 기능 지도 폴더 밖의 파일이 그 ID 를 가리킨다. `.md`·`.txt` 가 아닌 파일이면 어느 줄이든, `.md` 면 실행 명령(`node`, `npm`, `pytest`, `./x.sh` 등)이 있는 줄만. 또는 이름 파일의 `verified_by` 가 짚은 시험이 실제로 있다(아래 3단계). 근거 파일과 줄을 HTML 에 보인다 |
| 방법만 | 그 기능 파일의 `Driving it with …` 절에 ID 가 나온다. 사람이나 에이전트가 손으로 몰 방법은 있지만 돌릴 스크립트는 없다 |
| 없음 | 둘 다 아니다 |

Driving 글머리에 ID 가 없으면 방법이 적혀 있어도 「없음」으로 센다. 고칠 곳은 지도다. 글머리 앞에 그 하위 기능 ID 를 붙인다.

**MECE.** 기능 지도는 수학적으로 MECE 여야 한다. 진입점 집합을 기능들로 나눈 분할이다.
- 진입점마다 주인 기능이 정확히 하나다(`owner`). 주인은 그 진입점이 여는 화면·처리기를 맡은 기능이다. 그 진입점을 이름만 나열한 기능(홈 화면의 탭 목록, 설정의 메뉴 줄)은 주인이 아니다.
- 주인 기능 파일의 `Sub-features` 나 `How to get to it` 절에 그 진입점의 `match` 글자가 낱말째 있어야 한다. 앞부분만 겹치는 것(`⌘E` 와 `⌘Enter`)은 세지 않는다.
- 주인이 아닌 기능 파일의 그 두 절에는 그 진입점이 없어야 한다(ME).
- 기능이 아닌 것(영역 이름, 닫기 단추)만 `exclude` 에 이유를 달아 뺀다. 그래서 진입점 수 = 주인 있음 + 제외 + 주인 없음 이고, 주인 없음이 0 이어야 한다(CE).
- 하위 기능 ID 는 지도 전체에서 하나뿐이다.
스크립트가 이 넷을 검사해 `mece_problems` 로 센다. 0 이 아니면 지도가 MECE 가 아니다. README 는 보지 않는다. 색인 표와 「Not mapped yet」 절이 진입점을 이름만 대기 때문이다.

**README 빈칸.** README 의 `## Not mapped yet`(또는 「지도에 없음」) 절 글머리를 따로 보인다.

## 순서

1. **지도를 찾는다.** `<저장소>/.claude/skills/verify-*/features/` 다. 없으면 이 스킬을 멈추고 `/dev:verify-setup` 으로 지도부터 만든다. 지도 없이 HTML 을 꾸며 내지 않는다.
2. **진입점 목록을 뽑는다.** 코드에서 진입점의 진실 원천을 찾는다. 앱 종류마다 다르다.
   - 화면 앱: 단축키 표, 메뉴 정의, 라우터, 화면 탭 목록.
   - 백엔드: HTTP 라우트 등록(`HandleFunc`, `app.get`, `@router.post`, OpenAPI 명세), RPC·gRPC 서비스 정의, CLI 하위 명령, 예약 작업(cron), 큐 소비자, 웹훅.
   - 라이브러리: 바깥에 내보내는 공개 API(`index.ts` 의 export, `__all__`, `lib.rs` 의 `pub`, 패키지의 공개 클래스·함수).
   `group` 은 이 종류를 사람이 읽는 이름으로 쓴다(「HTTP · /api」, 「CLI 명령」, 「공개 함수」). 그래프 왼쪽 열이 이 묶음이다. 손으로 고르지 말고 그 원천을 읽는 짧은 스크립트로 뽑아 scratch 폴더에 JSON 으로 쓴다. 원천이 여럿이면 다 합친다. 원천이 없는 앱이면 이 단계를 건너뛰고 보고에 「진입점 목록 없음」 이라고 쓴다.
   ```json
   [{"id": "openSettings", "label": "openSettings", "group": "단축키 · 어디서나", "where": "src/shortcuts.ts:15", "match": ["⌘,"], "owner": "SETTINGS"},
    {"id": "--staged", "label": "kakapo --staged", "group": "CLI 인자", "where": "src/cli-args.ts:26", "match": ["--staged"], "owner": "OPEN"},
    {"id": "closeMenu", "label": "메뉴 닫기", "group": "머리·서랍 단추", "where": "src/Drawer.tsx:40", "match": ["메뉴 닫기"], "exclude": "서랍을 닫는 단추라 기능이 아니다"}]
   ```
   `match` 는 기능 파일에 적힐 글자 그대로다(키 표기, 플래그, 라우트 경로, 함수 이름, 버튼 이름). `where` 는 그 진입점이 정의된 `파일:줄` 이다. `owner` 는 기능 ID 나 기능 파일 이름이다. 코드에서 정한다: 라우트가 그리는 화면, 단축키가 부르는 동작, 명령이 들어가는 처리기를 따라가 그것을 맡은 기능을 고른다. 맡은 기능 파일이 없으면 그 화면 이름으로 `owner` 를 적는다. 스크립트가 「주인 기능 파일 없음」 으로 잡고, 6단계에서 그 파일을 만든다.
3. **지도에 이름을 쓰고, 근거 파일을 쓴다.** 기능 파일을 모두 읽고 H1 과 `Sub-features` 글머리가 위 「이름과 설명」 형식이 아니면 지도를 고친다(5단계와 같이 커밋한다). 그다음 scratch 폴더에 근거 파일(`--names`)을 쓴다. 지도에 담지 않는 것, 곧 `verified_by` 만 둔다.
   ```json
   {"NEED-2": {"verified_by": ["need_revive_test.go::TestNeedRevive"]}}
   ```
   백엔드·라이브러리 시험은 하위 기능 ID 를 담지 않는 일이 많다. 그 하위 기능을 실제로 검사하는 시험을 읽어 찾았으면 `verified_by` 에 `<저장소 기준 경로>::<시험 이름>` 으로 단다. 스크립트는 그 파일에 그 이름이 있을 때만 「자동 검증」으로 치고, 없으면 「근거를 못 찾음」 을 `naming_problems` 로 센다. 시험 본문을 읽지 않고 이름만 보고 달지 않는다.
4. **HTML 을 만든다.**
   ```bash
   python3 <이 스킬>/scripts/featuremap.py <저장소>/.claude/skills/verify-<앱>/features --repo <저장소> --surfaces <scratch>/surfaces.json --names <scratch>/names.json --out <scratch>/<앱>-featuremap.html
   ```
   표준 출력 첫 줄은 요약 JSON 이다. `naming_problems` 가 0 이 아니면 그 줄을 보고 지도(이름·설명)나 근거 파일(`verified_by`)을 고쳐 0 이 될 때까지 다시 만든다. 이어서 MECE 문제 줄(「주인 안 정함」, 「주인 기능 파일 없음」, 「주인 기능 파일에 안 적힘」, 「겹침」, 「하위 기능 ID 겹침」)과 「방법 없음 <기능> <ID>」 줄이 나온다. HTML 은 저장소에 커밋하지 않는다. 매번 지도에서 다시 만든다.
5. **지도를 MECE 로 만든다.** `mece_problems` 가 0 이 될 때까지 지도를 고치고 4로 돌아간다. MECE 가 아닌 지도로 HTML 을 내밀지 않는다.
   - 주인 기능 파일 없음: `/dev:verify-setup` 의 형식으로 그 화면의 기능 파일을 새로 만든다(H2 넷, 하위 기능 ID, How to get 에 그 진입점).
   - 주인 기능 파일에 안 적힘: 주인 파일의 How to get 이나 그 하위 기능 글머리에 진입점을 적는다.
   - 겹침: 주인이 아닌 파일에서 그 진입점을 지운다. 탭·메뉴 이름을 늘어놓은 줄이면 줄째 지우거나 진입점이 아닌 말로 바꾼다.
   - 주인 안 정함: 코드를 따라가 `owner` 를 정한다. 기능이 아니면 이유를 단 `exclude`.
   지도는 저장소의 검증 정본이라 고친 지도는 그 저장소 규칙대로 커밋·PR 한다. 코드는 고치지 않는다.
6. **띄워 본다.** 브라우저로 연다. 파일 경로로 열리지 않으면 그 폴더를 `python3 -m http.server` 로 띄운다. 처음 열 때 노드가 열 순서로 들어오고 선이 그려지는지, 고른 길에 흐름이 도는지 본다. 그래프 전체(축소해서 세 열이 다 보이게), MECE 배지와 탭, 검증된 기능 노드, 흐린(검증 안 된) 노드, 진입점 묶음 노드, 검색, 목록 탭, 휴대폰 너비와 아래 시트, 어두운 화면을 하나씩 눌러 보고 화면마다 한 장씩 찍는다. 휴대폰에서 그래프가 화면보다 넓어 끝점 이름이 잘리지 않는지 본다. 숫자가 표준 출력의 요약과 같은지 본다.
7. **이상한 숫자를 판다.** 자동 검증으로 잡힌 근거 줄을 몇 개 열어 정말 그 하위 기능을 돌리는지 본다. 주인 있는 진입점 몇 개를 골라 주인 파일의 그 줄이 정말 그 진입점으로 그 기능에 닿는 말인지 본다. 짧은 키(`Tab`, `F1`)는 엉뚱한 글에 걸렸을 수 있다. 틀린 판정을 찾으면 스크립트를 고치고 `--self-test` 에 그 경우를 더한다.

## 보고

- HTML 파일을 사용자에게 보낸다(파일 보내기 도구가 있으면 그것으로). 경로만 적지 않는다.
- 보고에서 기능을 부를 때도 `CMP-3 branch tip` 처럼 HTML 과 같은 영어 이름을 쓴다.
- 첫 줄에 「MECE ✓」 와 세 숫자를 쓴다. 자동 검증 a/n, 검증 방법이 있는 하위 기능 b/n, 주인 있는 진입점 c/(m - 제외). MECE 를 맞추려고 고친 지도 파일과 PR 도 같이 쓴다.
- 「없음」 하위 기능은 기능별로 세어 한 줄씩. 다 늘어놓지 않는다. 다 보려면 HTML 을 본다.
- 다음에 할 일은 검증을 늘리는 쪽으로 쓴다. 「방법만」 하위 기능에 드라이브 스크립트나 시험을 붙이면 자동 검증이 된다.
- 이 스킬은 지도만 고친다. 앱 코드는 고치지 않는다.
