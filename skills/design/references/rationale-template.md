# 설명 글 틀

타입 스케치와 함께 내는 글. 한 쪽. 제목은 문장형, 상투 문구 없이. 각 절의 안내문을 실제 내용으로 바꾼다.

## Problem

*한 문단. 무엇을 하려는지, 그리고 기존 시스템이나 제약의 무엇 때문에 모양이 뻔하지 않은지. [A 단계](../SKILL.md#a-ground-문제를-땅에-붙인다)에서 설계가 지켜야 할 제약(맞물려야 할 기존 타입, 깨면 안 되는 호출자, 경계를 넘어온 불변식)이 나왔으면 여기 적어 읽는 사람이 같은 제약을 보게 한다.*

## Usage (호출자 쪽에서 본 모습)

*타입 스케치보다 먼저 쓴다. 사용자가 읽을 README 나 빠른 시작, 그리고 그들 코드 안의 현실적인 호출 지점 두세 개. 무엇을 import 하고, 무엇을 부르고, 무엇이 돌아오는지. [Shape](#shape) 의 타입 스케치는 여기서 끌어낸다. 둘은 일치해야 한다. 어긋나면 사용 예가 아니라 스케치를 고친다. 호출자의 경험이 명세다. 타입은 그것을 섬긴다.*

## Shape

*추천하는 아키텍처. 데이터 구조를 먼저. 그다음 데이터가 시그니처를 어떻게 흐르는지. 무게를 받치는 결정을 이름으로 적는다. 어떤 불변식이 타입에 들어 있는지, 검증이 어디 있는지, 시스템이 일부러 하지 않는 것이 무엇인지 적는다. 인터페이스 깊이를 분명히 판단한다. 공개 면이 숨기는 복잡도, 호출자에게 남는 것, 인터페이스가 왜 더 크지 않은지. 결정마다 근거 원칙을 이름으로 단다(예: `../../mode/principles.md` 의 Boundary Discipline). 원칙 내용을 다시 풀어 쓰지 않는다.*

## Synthesis decision

*경쟁 절차([../SKILL.md](../SKILL.md#경쟁-절차))가 채운다. 어느 후보가 기반이 됐고 왜인지, 다른 후보 각각에서 무엇을 가져왔는지, 무엇을 왜 버렸는지. 모든 모델이 같은 회사라 심사 독립성에 한계가 있다는 점도 적는다.*

## Tradeoffs accepted

*고른 모양이 하는 맞바꿈마다 한 줄. 꼴은 「X 를 받아들이고 Y 를 얻는다」. 나중에 읽는 사람이 실수로 오해할 만한 것, 이른 최적화나 이른 단순화로 보일 만한 것을 적는다.*

## Alternatives considered

*필수. 구체적인 다른 모양을 최소 하나 적고, 왜 졌는지 한 줄. 대안은 구현이 단순한지만이 아니라 인터페이스 깊이로 판단한다. 호출자에게 드러내는 복잡도와 숨기는 복잡도를 적는다. 설계 공간에 진짜 경쟁자가 있었으면 두세 개. 제약이 답을 강제했으면 하나로 되고, 결론은 「이것만 가능했다. 왜냐하면…」 꼴로 쓴다. 같은 모양의 변형을 나열하지 않는다. 이 절은 고른 모양이 검토하고 버린 설계 대안이지 다른 러너의 후보가 아니다.*

## Open questions and risks

*스케치하며 알아챈 것 가운데 사람이 판단해야 할 것, 구현 전에 알릴 위험. 단정이 아니라 질문 꼴로 써서 사람의 답이 곧 해결이 되게 한다. 사람이 판단해야 할 것은 취향·제품 결정만 남긴다. 실행해서 알 수 있는 것은 여기 두지 않고 직접 확인한다.*

## Next implementation step

*스케치에 맞춰 처음 지을 것. 한 문장. 합성 직후(확인 단계를 골랐다면 승인 직후) 바로 쓰기 시작할 것.*
