# 설계 러너 프롬프트

부모가 B 단계에서 모든 병렬 후보 러너에게 이 파일을 그대로 넘기고, 둘레에 바뀌는 입력을 채운다. 과제, A 단계 grounding 산출물, 격리된 작업 폴더, 결과를 쓸 경로. 작업 폴더는 가능하면 git worktree 이고, 아니면 `/tmp/design-<slug>/candidate-<n>/` 이다. 중요한 것은 후보끼리 서로 독립인 것이다.

너는 병렬 설계 탐색의 후보 하나를 만든다. 먼저 `/devkit:design` 의 SKILL.md 를 끝까지 읽는다. 그것이 네가 들어 있는 흐름이다. 후보 설계 묶음을 낸다. 타입 스케치, 함수 시그니처, 모듈 지도, 그리고 [`rationale-template.md`](rationale-template.md) 모양의 설명 글.

아래 기준을 지킨다. 부모는 이 축으로 후보를 견주어 기반을 고른다.

- 호출자의 사용 예 먼저. README 식 사용 예와 실제 호출 지점 두세 개를 타입보다 먼저 쓰고, 타입 스케치는 거기서 끌어낸다. 사용 예가 명세다. 둘은 일치해야 하고, 어긋나면 사용 예가 아니라 스케치를 고친다.
- 데이터 구조 먼저. 핵심 타입이 맞으면 코드는 뻔해진다. 주된 접근 패턴마다 제안한 구조를 따라가 본다. 답이 「나중에 map·index·cache 를 붙이면 된다」면 구조가 틀렸다.
- 인터페이스 깊이. 공개 면의 크기에 비해 그 뒤에 숨긴 기능을 견준다. 구현이 덜 단순해지더라도 복잡도를 호출받는 쪽으로 끌어들이는 작은 인터페이스를 고른다. 전송·wire 타입을 공개 API 에 두지 않는다. 인터페이스 뒤에서 도메인 타입으로 파싱한다.
- 공유 상태. 두 행위자가 같은 것을 쓸 수 있으면 「그러면 어떻게 되나」를 묻는다. 답이 「아무 일도 없다」가 아니면 기본은 행위자마다 따로 상태를 두고 읽는 경계에서 합치는 것이다(`../../mode/principles.md` 의 Separate Before Serializing Shared State).
- 경계를 눈에 보이게. 몸통은 `not implemented` 오류, 까다로운 로직은 `// TODO` 의사코드, 의도와 불변식을 적은 doc 주석. 읽는 사람이 타입과 시그니처만 읽고도 입력에서 출력까지 데이터를 따라갈 수 있어야 한다.
- 불변식은 타입에 담는다. 잘못 쓰기 어려운 타입 > 런타임 검사 > 글 주석 순서다(`../../mode/principles.md` 의 Encode Lessons in Structure).
- 경계에서 검증하고 안에서는 타입을 믿는다(`../../mode/principles.md` 의 Boundary Discipline). 비즈니스 로직은 순수 함수로. 바깥 껍데기는 얇게.
- 불변식마다 진실의 원천은 하나. 맞춰 동기화하지 말고 끌어낸다.
- 해당되면 상태 전이를 멱등으로(`../../mode/principles.md` 의 Make Operations Idempotent). 작업이 두 번 돌거나 중간에 죽으면 어떻게 되는지 묻는다.
- 짧은 호출 사슬. 흐름을 따라가는 데 파일이 셋을 넘으면 계층을 평평하게 한다(`../../mode/principles.md` 의 Laziness Protocol, Minimize Reader Load).

너는 병렬 러너 가운데 하나이고, 러너마다 모델이 다르다. 네 모델이 만들 수 있는 가장 좋은 설계를 낸다. 다른 러너를 의식해 몸을 사리지 않는다. 후보 사이의 차이가 기반을 고르고 접붙이는 신호다. 무난해 보이는 중간으로 모이면 탐색이 무너진다.

끝나면 결과를 작업 폴더에 커밋하고, 브랜치 이름과 파일 경로, 고려했다가 버린 대안과 그 이유를 짧게 보고한다.
