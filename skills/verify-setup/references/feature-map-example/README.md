# Notes 검증 지도

이 폴더는 Notes 의 사용자 동작을 검증하는 관리된 정본이다. 앱을 몰기 전에 이 색인을 읽고, 맞는 기능 파일을 방법으로 쓴다.

## 기본 전제

- 버려도 되는 데이터 폴더로 `http://127.0.0.1:4173` 에 Notes 를 띄운다.
- 동시 실행이 상태를 나누지 않게 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` 를 둔다.
- 제목이 `Quarterly plan` 과 `Grocery list` 인 노트를 시드로 넣는다.
- `control-notes` 와 `notes` CLI 를 `PATH` 에 둔다.
- `control-notes doctor` 를 돌리고 기대한 URL, 데이터 폴더, 빌드 리비전을 요구한다.
- 이 검증 실행이 띄우지 않은 인스턴스는 몰지 않는다.

## 몰기 관례

- 전제에 다른 말이 없으면 모든 방법은 기본 상태에서 시작한다.
- CSS 선택자나 DOM 위치보다 ARIA 역할과 접근 가능한 이름을 쓴다.
- 모든 명령은 글자 그대로 다룬다. 따옴표 속 이름과 플래그를 바꾸지 않는다.
- 브라우저 동작은 `control-notes browser` 로 한다.
- 터미널 동작은 `control-notes cli -- <명령>` 으로 한다.
- 무언가를 바꾼 뒤에는 시드 데이터를 되돌린다. 정리할 때 증명 산출물은 지우지 않는다.

## 증명과 건너뜀 보고

- 마지막 화면만이 아니라 사용자 행동과 그 결과 상태를 잡는다.
- UI 증명에는 ARIA 스냅숏과 앱 이름이 보이는 스크린샷이 들어간다.
- CLI 증명에는 명령, stdout, stderr, 종료 코드가 들어간다.
- 값을 바꾼 증명에는 저장된 값을 다른 읽기 전용 화면으로 다시 본 것이 들어간다.
- 산출물마다 기능 ID 와 쓴 진입점을 적는다.
- 닿을 수 없는 경로는 시도한 명령과 채워지지 않은 전제를 보고한다.
- 건너뛴 진입점을 다른 경로로 검증했다고 보고하지 않는다.

## 기능 파일 약속

기능 파일은 H1 제목과, 사용자에게 보이는 동작을 설명하는 문단 하나로 시작한다. 그다음 H2 넷을 이 순서로 정확히 쓴다.

1. `Sub-features` 는 짧은 ID 와 동작마다 한 줄을 적는다.
2. `How to get to it (user POV)` 는 사용자 진입점을 모두 적는다.
3. `Driving it with <장치>` 는 `Preconditions:` 로 시작하고, 사용자 행동마다 정확한 명령과 관찰할 결과를 짝지은 라벨 붙은 글머리를 쓴다.
4. `Gotchas` 는 검증 실행을 낭비하거나 무효로 만들 수 있는 함정을 적는다.

구현 세부는 지도에 넣지 않는다. 사용자 경로, 안정된 손잡이, 필요한 상태, 명령, 관찰할 수 있는 증명만 쓴다.
