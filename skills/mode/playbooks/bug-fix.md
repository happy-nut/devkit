# 버그 수정

**언제.** 보고된 결함을 재현하고, 근본 원인을 찾고, 런타임 증거로 고친다.

**소유.** 이 작업을 소유한다. 계획하고, 리뷰하고, 검증한다. 원인 조사와 수정은 서브에이전트(`subagent_type: "devkit:worker"`)에 맡기고 리드는 놓지 않는다.

과학적으로 한다. 내보내는 모든 줄은 런타임 증거로 이어진다. 「도움이 될지도」 싶은 이중 안전장치는 가설이지 수정이 아니다. 내보내지 않는다. 증거가 가설을 반박하면 그 가설 때문에 넣은 변경을 되돌린다. 증거가 정당화하는 가장 작은 변경만 내보낸다.

## 단계

1. 같은 표면에서 직접 재현한다.
   웹 화면은 브라우저 도구(Claude in Chrome, 내장 브라우저, playwright), CLI·서버는 터미널에서 돌린다. 디버그·계측 절차 문서가 「사용자에게 재현을 부탁하라」고 해도 직접 한다. 사용자에게 부탁하는 것은 그 표면이 대상에 닿지 못하는 구체적 이유가 있고, 닿는 데까지 끝까지 몰아 본 뒤뿐이다. 바로 재현되지 않으면 계기를 합성하거나, 조건을 조이거나, 계측을 넣어 터질 때까지 간다. 화면 버그는 재현 화면을 스크린샷으로 남긴다.
2. 원인을 이분 탐색으로 좁힌다.
   후보 가설을 세우고 하나만 남을 때까지 지운다. 가설의 씨앗은 영향받는 하위 시스템의 추적과 `/devkit:why`(회귀 이력)다. 매 회차 남은 문제 공간을 가장 많이 자르는 분할을 골라 런타임 증거를 얻고 지운다. 프로그램 상태가 불분명하면 계측이나 로그를 넣고 실행 중에 읽는다. 짐작하지 않는다. 길고 끈질긴 추적은 Claude Code `/loop` 스킬이나 ScheduleWakeup 으로 몬다. 3단계의 설계·리뷰 팬아웃 전에 살아남은 *메커니즘*을 런타임 증거로 확정한다. principles.md 의 Fix Root Causes 대로, 처음 잘못된 곳을 고친다.
3. 수정을 계획한다.
   함수 경계를 넘으면 먼저 `/devkit:design`. 구현은 범위를 구체적으로 정해 서브에이전트에 맡긴다. 모델은 `opus`, 교차 설계·까다로운 동시성·미묘한 알고리즘이면 `fable`.
4. 같은 표면에서 검증한다.
   원래 재현이 이제 통과해야 한다. 「판단 불가」나 다른 표면에서의 통과는 통과가 아니다. 그렇게 표시한다. 단위 테스트는 분기 동작을 보여 줄 뿐 버그가 없다는 증명이 아니다. 화면 버그는 고친 화면을 다시 띄워 스크린샷으로 확인하고, 백엔드 값만 보지 말고 화면에 나온 값까지 따라간다. 잘 되던 것이 망가지지 않았는지도 본다.
5. 실패하는 재현이 수정보다 먼저 git 이력에 들어가게 커밋을 나눈다.
   값싼 로컬 테스트 경로가 있으면 `/devkit:tdd` 의 실패 테스트 먼저 순서를 따른다. 테스트가 비싸거나, 통합 위주이거나, 모양이 불분명하면 생략한다. principles.md 의 Sequence Work into Verifiable Units 의 정석이다. 실패 테스트가 먼저, 수정이 그 위.
6. `opening-a-pr.md` 로 PR 을 연다.

## 답변에 넣을 것

- 무엇이 깨졌나, 근본 원인, 수정, 검증 방법.
- 실패하던 재현 출력과 통과하는 재현 출력을 그대로 붙인다. 화면이면 전후 스크린샷.
