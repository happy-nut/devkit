# 트레이스 포렌식

**언제.** 이미 잡아 건네받은 프로파일 산출물(cpuprofile, trace, spindump, 힙 스냅샷)로 사후 진단한다. 살아 있는 프로세스를 계측하는 일은 `runtime-forensics.md` 다.

**소유.** 산출물에서 나온 진단을 소유한다. 산출물은 고정된 데이터다. 읽기만 하고 다시 돌리지 않는다. 도구는 일반적인 것을 쓴다. cpuprofile 과 `.json.gz` 는 DevTools 나 trace 파서, spindump 는 텍스트로, 힙 스냅샷은 힙 도구로.

## 단계

1. 형식을 알아내고 맞는 도구로 연다.
   큰 산출물은 서브에이전트(`sonnet`)에서 파싱하고 줄인 결과만 본 스레드에 둔다(principles.md 의 Guard the Context Window).
2. 쿼리할 수 있는 모양으로 바꾼다.
   trace 나 힙 스냅샷을 sqlite 로 덤프한다. 샘플, 프레임, 노드 하나에 한 행. 읽기 전에 이 모양부터 만든다.
3. 원인으로 좁힌다.
   시간을 가장 많이 쥔 프레임을 쿼리하고 콜 트리를 따라 뜨거운 경로로 간다. 누수면 새는 객체에서 GC 루트까지 보유 사슬을 따라간다. spindump 면 CPU 에 붙었거나 막힌 스레드와 그 대기 사유를 찾는다.
4. 소스로 귀속한다.
   산출물 자체의 심볼로 뜨거운 프레임을 파일, 심볼, 줄에 매핑한다. 소스 매핑이 없는 프레임은 아직 진단이 아니다. 심볼을 풀거나, 산출물에 심볼이 없다고 분명히 말한다.
5. 짝이 되는 산출물이 있으면 전후를 diff 해 확인한다.
   없으면 그 결과를 확정 원인이 아니라 「산출물이 뒷받침하는 가장 강한 가설」로 표시한다.
6. 근거를 단 진단을 돌려준다.
   요청이 없으면 수정하지 않는다. 원인이 나오면 `bug-fix.md` 나 `perf-issue.md` 로 넘긴다. 처리량 점검은 한 줄로 둔다.
   `처리량 점검: n/a, 읽기 전용 포렌식`

## 답변에 넣을 것

- 산출물과 형식, 줄인 결과, 소스 위치, 산출물 경로.
- 짝 산출물로 확인했는지, 가설로 남았는지.
