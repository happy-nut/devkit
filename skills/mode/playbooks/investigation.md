# 조사

**언제.** 읽기 전용 질문이다. X 는 어떻게 동작하나, Y 는 왜 이렇게 만들었나, Z 는 확실한가, X 와 Y 중 무엇이 낫나.

**소유.** 답을 소유한다. 계획하고, 길을 정하고, 쓴다. 결과는 근거를 단 설명이나 추천이다. 코드 변경이 아니다.

## 단계

1. 질문이 가리키는 코드를 추적한다.
   동기를 묻는 질문(왜 이렇게 만들었나)이면 `/dev:why` 도 거친다.
2. 처리량 점검은 한 줄로 둔다.
   `처리량 점검: n/a, 읽기 전용 조사`
3. 산출물을 쓴다.
   기본 틀은 개요 / 핵심 개념 / 동작 방식 / 위치 / 함정 다섯 절이다. 대안 중 하나를 고르는 질문이면 트레이드오프 표와 추천을 쓴다.
4. 답을 `/dev:write` 기준으로 다듬는다.

PR, PR 돌보기, `/dev:design` 은 없다. 조사 결과 코드 변경이 필요하다고 나오면 답에 그 결론을 적고 멈춘다. 질문에는 답만 하고 바꾸지 않는다. 사용자가 고치라고 하면 그때 `bug-fix.md` 나 `feature.md` 로 다시 고른다.

## 답변에 넣을 것

- 조사 산출물.
- 「확실한가」류 질문이면 진짜 판단과 그 이유. 전제가 틀렸으면 반박한다.
- 주장마다 근거(파일 경로·줄, 실행 결과)나 「추론」「추측」 표시.
