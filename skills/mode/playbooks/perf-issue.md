# 성능 문제

**언제.** 측정된 느림을 기준선 대비 한 번 고친다. 목표 지표를 꾸준히 끌어올리는 일이면 `hillclimb.md`.

**소유.** 측정 이야기를 소유한다. 계획하고, 리뷰하고, 숫자를 검증한다. 모든 수정을 측정에 묶는다. 소스를 읽는 것으로 측정을 대신하지 않는다.

## 단계

1. 같은 표면에서 기준선 trace 를 잡는다.
   웹이면 playwright 로 CDP 성능 trace, 터미널 프로세스면 그 언어의 프로파일러(`py-spy`, `node --cpu-prof` 등). 기준선과 이후의 모든 숫자는 `/dev:bench` 로 검증한다. principles.md 의 Explain the Number 대로, 숫자를 믿기 전에 무엇이 그 숫자를 제한하는지 찾는다.
2. 코드를 추적해 가설을 세운다.
   돌려 보지 않고 성능 한계를 주장하지 않는다. 성능 주문을 싼 것부터 순서대로 시도한다.
   1. 하지 마라. 결과를 아무도 안 쓰는 일은 싸게 만들지 말고 멈춘다.
   2. 하되, 두 번 하지 마라.
   3. 덜 해라.
   4. 나중에 해라.
   5. 안 볼 때 해라.
   6. 동시에 해라.
   7. 싸게 해라.

   앞 단계가 목표에 닿으면 멈춘다.
3. trace 를 근거로 수정을 계획하고 맡긴다.
   함수 경계를 넘으면 먼저 `/dev:design`. 구현은 서브에이전트(`subagent_type: "dev:worker"`, 모델 `opus`)에 맡긴다. diff 를 리뷰한다. 수정 뒤 trace 를 다시 잡는다. principles.md 의 Sequence Work into Verifiable Units 대로 시도 하나를 검증한 뒤 다음 시도로 간다.
4. 산출물을 파싱해 비교한다.
   JSON 은 sqlite 로 옮겨 쿼리하고, 전후를 diff 한다. 「판단 불가」나 다른 표면의 결과는 통과가 아니다. 그렇게 표시한다. 화면에서 느끼는 속도가 문제였으면 화면에서 다시 재 본다.
5. PR 에 측정을 인용한다.
   전후 숫자, 측정 명령, 반복 횟수, 걸린 시간을 적는다.
6. `opening-a-pr.md` 로 PR 을 연다.

## 답변에 넣을 것

- 기준선 숫자, 수정 뒤 숫자, 차이.
- 산출물 경로.
