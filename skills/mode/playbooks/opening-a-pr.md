# PR 열기

**언제.** 다른 모든 플레이북의 끝에서 부른다.

**소유.** PR 의 모양을 소유한다. 커밋 순서, 제목, 본문, 크기, 스택 구조.

## 단계

1. 메인에서 딴 git 워크트리에서 일한다.
   서브에이전트는 그 워크트리를 물려받는다. 같은 브랜치에 `Agent` 를 여러 번 띄우면 각자 `isolation: "worktree"` 로 따로 받거나, 사이마다 `git fetch && git reset --hard origin/<branch>` 한다. 브랜치에 관계없는 작업이 섞여 있으면 패치로 빼고, 새 워크트리를 만들고, 패치를 적용한다. 워크트리가 엉키면 main 에서 다시 따고 최소로 다시 한다.
2. 커밋을 넉넉히 하고, PR 을 열기 전에 작고 순서 있는 커밋으로 rebase 한다.
   커밋 하나는 앞으로의 PR 하나다. 홀로 착지할 수 있고, 이야기 순서대로 놓인다. 고친 것이 방금 만든 커밋에 속하면 amend, 떼어 낼 수 있으면 새 커밋. 커밋 본문은 제목을 되풀이하지 않는다.
3. 커밋 전에 diff 를 정리하고, 리뷰 전에 주석을 지운다.
   커밋 전에 `/simplify` 를 돌리거나 diff 를 직접 다시 읽어 서술 주석, 근거 없는 방어 코드, 죽은 호환 경로, 관계없는 수정을 지운다. 리뷰 전에 `/devkit:no-comments`. PR 제목, 본문, 커밋 본문은 `/devkit:write` 로 쓴다(동작 하나에 낱말 하나, `-ing` 같은 명사화 대신 평범한 동사). 손님이 읽는 글이 diff 에 있으면 korean-humanizer 를 거치고 본문에 「휴머나이즈 거침」을 한 줄 적는다.
4. 제목은 Conventional Commits `type(scope): subject` 로, 끝에 마침표 없이 쓴다.
   type 은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf` 같은 것. scope 는 영역(`api`, `web` 등). subject 는 짧은 명령형이고, 변경을 실어 나르는 실제 심볼이 있으면 그 이름을 쓴다. 예 `fix(mode): opening-a-pr 의 babysit 시점 바로잡기`. 제목·본문 언어는 저장소 이력을 따른다.
5. 본문은 diff 를 가진 리뷰어를 위한 1분 브리핑으로 쓴다.
   실험 노트가 아니다. 왜 있는지, 무엇을 빼는지, 무엇을 깰 수 있는지, 어떻게 증명했는지를 쓴다. 짧고 쉬운 문장, 식별자는 적게, 글 벽 없이. 본문은 squash 커밋 본문이 되니 그 커밋이 40줄 안팎을 넘지 않게 한다. 굵은 머리말 말고 `##` 제목을 아래 순서로 쓰고, 할 말이 없는 절은 뺀다. 저장소 `AGENTS.md`·PR 템플릿이 형식을 정하면 그것이 먼저다.
   - `## 왜`: 사용자의 목표로 시작한다. 문제와 접근을 1~3 짧은 문장. SHA, rebase 계보, 「main 기준」 같은 서두는 쓰지 않는다.
   - `## 바뀐 것`: 짧은 항목 1~3개. 변경을 실어 나를 때만 실제 심볼·경로를 쓴다. 이름 바꾸기·대상 바꾸기는 양쪽 이름을 다 쓴다.
   - `## 범위`: 늘 쓴다. 무엇을 다루고 무엇을 일부러 빼는지(후속, 알려진 빈틈) 1~3개. 심볼, 경로, 파일별 설명 없이.
   - `## 트레이드오프`: 리뷰어가 물어볼 만한 버린 대안만. 진짜 선택이 없었으면 뺀다.
   - `## 파급 범위`: 누구·무엇에 닿고 왜 안전하거나 위험한지 1~2 문장. main 이 빨간색이면 빨간 채로 두는 비용을 쓴다.
   - `## 검증`: 항목 1~3개, 각각 실제로 돌린 경로와 결과. 성능은 대표 숫자 하나를 단위와 함께 `전 → 후` 로 쓰고 나머지는 `/devkit:design`·`/devkit:swarm` 결과 폴더 링크로. 표본 크기 방법론, 스웜 낭독, 지표 표는 쓰지 않는다.
   절 뒤에 주장을 증명하는 스크린샷·영상을 붙인다. 화면 변경이면 기능마다 한 장. 전체 SHA, 스웜·설계 레인 낭독, 파일별 체크리스트, 「CLEAN」 판정은 본문 말고 링크한 산출물에 둔다. 커밋 본문·PR 본문 끝에는 세션이 주는 attribution 줄을 붙인다.
6. PR 도구를 한 번 정하고 만들기·고치기·조회·감시·머지 내내 그것을 쓴다.
   기본은 GitHub CLI `gh`. `command -v gt` 가 성공하고 이 저장소에서 `gt log short` 가 돌면 스택 만들기·restack·submit 은 Graphite `gt` 로 하고, 조회·코멘트·머지는 `gh` 로 한다. `gt` 가 없으면 전부 `gh` 로 하고 그 사실을 기록한다. `gt` 를 요구하지 않는다. 세션이 PR 을 추적하는 도구를 주면(데스크톱 앱의 PR 연결 등) 만든 PR 을 거기에 연결한다.
7. 큰 PR 하나보다 좁은 PR 다섯 개를 고른다.
   스택은 base 브랜치 사슬이다. 뿌리 PR 은 trunk 를 겨눈다. 자식 브랜치는 부모의 정확한 끝에 rebase 하고 PR 은 부모 브랜치를 겨눈다. 부모가 머지되면 `shipping.md` 4단계대로 자식을 trunk 로 옮긴다. 자식은 `gh pr create --base <parent-branch>`(또는 `gt create` 뒤 `gt submit`)로 만들고, 대상을 바꿀 때는 `gh pr edit <pr> --base <parent-branch>`. trunk 에서 따는 것은 독립 작업뿐이다. 스택 작업을 크게 하기 전에 trunk 에 rebase 한다.
8. PR 은 늘 ready 로 연다. draft 로 열지 않는다.
   `gh pr create` 에 `--draft` 를 붙이지 않는다. 그래도 draft 로 열리면 `gh pr ready <number>`. PR 상태를 말하기 전에 `gh pr view <number>` 를 돌린다.
9. PR 을 열었다고 babysit 을 시작하지 않는다.
   URL 을 올리고 계속 만든다. phase 나 스택을 먼저 끝낸다. 스택 전체가 생긴 뒤 사용자가 시킬 때만 따로 babysit 한다. 새 PR 마다 babysit 하면 만들기가 멈추고, 뒤 웨이브가 다시 돌릴 커밋에 CI 를 쓴다. 피드백이 의도에서 벗어나면 반박한다. 개인 저장소에서 사용자가 「고쳐」라고 했으면 그 말이 CI 통과와 머지까지라서 스택이 다 생긴 뒤 `babysit.md` 와 `shipping.md` 로 이어 간다.

PR 을 여는 서브에이전트는 diff 정리와 `/devkit:no-comments` 를 거치고 URL 을 올린 뒤 babysit 없이 부모에게 돌아온다. 예외는 `autopilot-full.md`·`autopilot-stack.md` 의 담당이다. 그 담당의 브리프가 babysit 루프를 맡기고, 그것이 `babysit.md` 가 기다리는 요청이다. 담당은 코드 준비 보고 뒤 루프를 시작하고 머지 준비를 보고하며, 여기와 `babysit.md` 의 「스택이 다 생길 때까지 babysit 보류」 규칙에서 빠진다.

**회사 저장소.** 개인/회사 구분은 `/devkit:mode` 의 「저장소 구분」로 회사면. 자기 브랜치 push 와 PR 열기는 하되, 공유 브랜치 push 와 머지는 사용자가 그 말을 했을 때만 한다.

## 답변에 넣을 것

- PR 링크(`https://github.com/<owner>/<repo>/pull/<number>`)와 스택 순서.
- 쓴 PR 도구(`gh` 또는 `gt`)와 대체했으면 그 사실.
