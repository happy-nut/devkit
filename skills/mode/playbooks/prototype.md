# 프로토타입

**언제.** 디자인이나 동작 결정을 싸게 내리려고 버릴 스케치를 만든다. 사람에게 묻는 대신 관찰로 갈림길을 정할 때도 쓴다(「프로토타입」, 「목업」, 「이 배치 해 봐」, 「스케치해서 정하자」).

**소유.** 코드가 아니라 디자인 결정을 소유한다. 프로토타입은 버리는 도구다. 실제 구현은 `feature.md` 를 따른다.

Laziness Protocol 의 「가장 작은 변경」과 검증 기준이 뒤집히는 유일한 플레이북이다. 다듬기보다 속도, 코드 품질은 상관없고, 계획도 없다. 엄밀함은 맞는 디자인을 싸게 고르는 데 있다. 사용자가 말하지 않은 변형도 내놓고, 한 접근을 버리고 다른 것을 해 본다.

## 단계

1. 프로토타입이 내릴 결정의 범위를 정한다.
   어떤 배치, 어떤 상호작용, 어떤 밀도. 실험으로 정할 갈림길이면 어떤 동작, 타이밍, 접근. 내릴 결정이 없으면 프로토타입도 없다. `feature.md` 로 간다.
2. 디자인 공간이 열려 있으면 레퍼런스를 모은다.
   선례를 찾고, 테마·팔레트·배치를 무드보드로 요약한다. 방향은 직접 가장 나은 쪽을 고르고 이유를 적는다. 순수한 취향이라 실험으로 못 정할 때만 AskUserQuestion 으로 하나 묻는다. 방향이 정해져 있으면 이 단계를 건너뛴다. 저장소에 디자인 시스템이 있으면 거기 있는 것부터 쓴다.
3. 생산 소스와 떨어진 scratch 디렉터리에 버릴 코드를 만든다.
   시각 결정은 바닐라 HTML/CSS/JS 나 아이디어를 그릴 수 있는 가장 가벼운 스택, CDN 의존성, 핫 리로드 dev 서버. 동작·타이밍 결정은 질문을 실행해 볼 가장 작은 스크립트. 생산용 프레임워크, 테스트, 추상화는 없다.
4. 대안을 비교하면 스위처 하나(버튼이나 키) 뒤에 두고 변형마다 이름표를 붙인다.
   principles.md 의 Exhaust the Design Space 를 싸게 하는 방법이다.
5. 같은 표면에서 확인한다.
   시각 결정은 브라우저 도구로 변형마다 스크린샷을 찍고 상호작용을 몰아 본다. 동작·타이밍 결정은 타이밍을 로그로 찍거나, 출력을 찍거나, 렌더를 지켜보며 정하려는 것 자체를 관찰한다. 여기서는 단언이 아니라 관찰이 테스트다.
6. 대안, 트레이드오프, 추천을 내놓는다.
   산출물은 결정과 버릴 코드이지 내보낼 코드가 아니다. 고른 방향은 `feature.md`(모양을 정할 일이면 `/dev:design`)로 넘겨 실제로 만든다.

## 답변에 넣을 것

- 탐색한 변형.
- 증거. 시각 결정은 변형마다 스크린샷, 동작 결정은 관찰한 출력이나 타이밍.
- 트레이드오프, 추천, scratch 경로.
- 프로토타입은 버릴 코드라는 말.
