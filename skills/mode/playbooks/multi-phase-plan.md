# 여러 단계·여러 PR 계획

**언제.** phase 여러 개나 쌓인 PR 여러 개에 걸친 일을 계획한다.

**소유.** 계획을 소유하고 코드는 소유하지 않는다. 계획은 담당이 칸마다 실행하고 사용자가 증거로 감사하는 체크리스트다. 계획이 산출물이다. 구현하지 않는다.

## 단계

1. 파일 한두 개에 접근이 뻔한 변경이면 계획을 건너뛴다.
   그렇다고 말하고 멈춘다.
2. 쓰기 전에 열린 질문을 프로토타입으로 정한다.
   질문마다 `prototype.md` 를 돈다. 부록 A 를 위해 브랜치, SHA, 스크린샷을 남긴다. 어떤 실행으로도 정할 수 없는 제품·취향 결정만 사용자에게 `AskUserQuestion` 으로 묻고, 선택지를 주고, 답을 기다리는 동안 나머지를 쓴다(principles.md 의 Never Block on the Human).
3. 서브에이전트로 탐색한다.
   `subagent_type: "dev:worker"`(읽기만이면 `"Explore"` 와 브리프에 「파일을 고치지 마라」), 모델은 넓게 읽기면 `sonnet`, 판단이면 `opus`(principles.md 의 Guard the Context Window). 각자 파일 위치, 관례, 시험 명령, 진입점을 돌려준다. 덤프를 붙여 넣지 않는다.
4. 아래 뼈대를 계획 파일에 복사하고 모든 자리 표시를 채운다.
   사용자가 경로를 말하지 않으면 저장소 밖 `~/.claude/plans/<slug>.md` 에 쓴다. 모든 제목과 하위 블록을 보이는 순서대로 둔다. PR 하나에 절 하나. PR 하나는 자기 증거를 가진 변경 하나다(principles.md 의 Sequence Work into Verifiable Units). **읽는 법** 에 실행 플레이북을 적는다. 실행이 머지까지 해도 되면 `autopilot-full.md`, 사용자가 PR 을 착지시키면 `autopilot-stack.md`. 회사 저장소는 사용자가 머지를 말하지 않았으면 `autopilot-stack.md` 다.
5. `/dev:write` 로 쓴다.
   본문은 how-to 한 갈래다. 설명과 참고는 부록에 둔다. 제목마다 할 일이나 발견을 말한다. 긴 대시를 쓰지 않는다. 문장 중간 쌍점을 쓰지 않는다.
6. `node <mode 스킬 폴더>/scripts/check-plan.mjs <plan.md>` 를 돌리고 찍힌 줄을 모두 고친다.
   principles.md 의 Encode Lessons in Structure. 문제가 0개가 될 때까지 다시 돌린다.
7. 넘긴다.
   계획 경로와 스크립트 출력을 올리고 멈춘다. 실행은 사용자가 시작을 분명히 말한 뒤에, 계획이 적은 실행 플레이북으로 한다.

**검증.** 테스트만으로는 검증이 아니다. PR 은 단위·실사용·성능 칸이 모두 체크돼야 검증된 것이다(principles.md 의 Prove It Works). 이 문장이 검증 규칙이다. 모든 검증 블록이 이 문장으로 시작한다. 실사용 블록은 필수다. PR head 에서 레인 열 개가 그 표면의 조종 수단으로 실제 표면을 몬다. `/dev:swarm` 대로, 모델은 `sonnet`. 레인 하나가 칸 하나이고, 구체 시나리오, 저장할 스크린샷, 통과 조건을 갖는다. 레인 하나는 **trunk 대비 회귀 레인** 이다. 같은 핵심 시나리오를 trunk 와 head 에서 돌린다. trunk 에 그 기능이 없으면 그 사실을 기록하고, trunk 결과를 지어내지 말고 diff 가 더한 동작과 사용자가 기다리는 최종 상태를 관문으로 삼는다. 성능 관문은 양쪽이다. trunk 와 head 가 모두 그 지표를 내야 한다. trunk 에 기능이 없으면 diff 가 더한 일을 따로 떼어 그 일과 사용자가 기다리는 처음부터 끝까지의 상태에 절대 예산을 둔다. 다른 시나리오끼리 비율을 주장하지 않는다. 성능 블록은 지표, 교대로 도는 측정, 먼저 잰 trunk 기준선, 실패하는 숫자를 가진 규칙을 적는다. 상호작용을 바꾸는 PR 은 리뷰 관문을 받는다. 사용자가 머지 전에 대화에서 스크린샷과 영상으로 리뷰한다. 상호작용을 바꾸지 않는 PR 은 `**리뷰 관문.** 없음. <PR id> 는 리뷰 관문 대상이 아니다.` 라고 쓰고 그 아래 칸을 두지 않는다.

**조종 수단.** 표면으로 고른다. 브라우저·Electron·웹 UI 는 브라우저 도구(Claude in Chrome, 내장 브라우저, playwright). CLI·TUI 는 터미널 실행. 네이티브 모바일은 시뮬레이터 도구나 저장소의 시뮬레이터 스킬. 앱마다 `/dev:verify-setup` 으로 만든 검증 스킬이 있으면 그것이 먼저다. 표면 두 개를 건드리는 PR 은 양쪽에 레인을 둔다. 조종 수단이 없는 표면은 부록 C 의 위험이고, 그래도 실사용 블록은 레인마다 어떻게 모는지 적는다.

````markdown
# <프로그램> 계획

<열 줄 미만. 무엇이 누구에게 바뀌는지, 프로그램이 지키는 규칙, 순서대로 PR id.>

## 읽는 법

칸 하나는 일 하나다. 칸마다 그것을 체크하는 증거를 적는다. 안쪽 칸은 위 칸의 하위 단계다. 증거가 있을 때만 칸을 체크한다. 증거는 파일, 로그 줄, 스크린샷, 시험 실행, SHA 다. 본문은 how-to 다. 부록은 설명하고 기록한다.

이 프로그램은 mode 스킬의 `playbooks/<실행 플레이북>.md` 를 돈다. <누가 머지하는지, 머지 준비에서 멈추는 사용자 몫 PR id.>

테스트만으로는 검증이 아니다. PR 은 단위·실사용·성능 칸이 모두 체크돼야 검증된 것이다.

- [ ] 프로그램 시작 때 아래를 읽는다. 매 틱 다시 읽는다.

  - [ ] mode 스킬의 `playbooks/<실행 플레이북>.md`

- [ ] 틱 프롬프트는 이 글 그대로 쓴다. "실행 플레이북을 다시 읽는다. 작업을 그것에 대어 감사하고 이번 틱에 표류를 고친다. 살아 있는 레인을 모두 살피고 진행은 부수 효과로만 판단한다. 막힌 레인은 물리고 대신할 것을 지금 띄운다. 그다음 감사가 앞 상태 메시지에 없던 추적 변화를 찾았을 때만 사용자에게 짧은 상태 메시지를 대화로 보낸다. PR 열림, 코드 준비 head, 회차 시작이나 끝, 판정, 머지, 막힌 에이전트와 한 조치, 막힘 생김이나 풀림, 사용자만 할 수 있는 결정 같은 것이다. 그런 변화를 모두 이름 짓고 그 밖의 것은 쓰지 않는다. 표, 머지 목록, 바뀌지 않은 막힘을 되풀이하지 않는다. 찾은 것이 없으면 답글 없이 턴을 끝낸다. 어느 쪽이든 이번 틱의 줄을 결정 기록에 남긴다. 그 줄은 보고한 항목이나 없음을 적는다."
- [ ] 사용자가 보류나 물러남을 말하면 모든 담당에게 바로 쓰기 0 지시를 보낸다.

### 담당 띄우기

- [ ] PR 마다 실행 플레이북이 정한 전체 수명을 가진 담당 하나를 `dev:worker` 로 띄운다.
- [ ] 이 의존 그래프를 따른다. 의존하는 일은 부모가 머지된 뒤에 시작하거나, 실행 플레이북이 쌓을 때는 부모 브랜치에 둔다.
  - [ ] <PR id> 와 <PR id> 는 독립이고 먼저 간다. 둘 다 `main` 에서 딴다.
  - [ ] <PR id> 는 <PR id> 뒤.
- [ ] 파일 경계를 지킨다. <PR id 나 묶음> 은 `<glob>` 만 건드린다.
- [ ] 리뷰 관문을 지킨다. <PR ids> 는 상호작용을 바꾼다. 머지 전에 사용자가 대화에서 스크린샷과 영상으로 리뷰하기를 기다린다.

### PR 절차, 모든 PR 에

- [ ] PR 도구를 한 번 정한다. 기본은 `gh`, `gt` 가 있고 저장소가 Graphite 를 쓰면 스택 조작은 `gt`. `gt` 를 요구하지 않는다. 대체했으면 기록한다.
- [ ] PR 은 **PR 열기** 대로 ready 로 연다. draft 로 열지 않는다. `gh pr create --base <base-branch>`. 스택 자식은 부모 브랜치를 겨눈다.
- [ ] PR 로 가는 push 전에 저장소 lint 와 타입 검사를 한 번 돌린다. 훅을 켠 채 push 한다.
- [ ] 커밋마다 전에 diff 를 정리하고(`/simplify` 또는 diff 다시 읽기) 리뷰 전에 `/dev:no-comments` 를 돌린다.
- [ ] 리뷰 봇과 사람 리뷰 코멘트를 mode 스킬의 `references/review-triage.md` 대로 모두 분류한다.
- [ ] 코드 준비 보고와 babysit 전에 지금 trunk 에 rebase 한다. 고치는 회차는 그 merge base 를 지킨다. 다시 rebase 하는 것은 머지 준비 때, trunk 와 `git merge-tree` 충돌이 날 때, trunk 변경 때문에 CI 가 실패할 때, 같은 파일을 바꾸는 알려진 동시 변경이 들어올 때뿐이다.

### 판정과 머지, 모든 PR 에

- [ ] 전체 스웜은 코드 준비 head 에서 한 번 돈다. 새 동작, 재설계, 큰 새 diff 일 때만 다시 돈다. rebase, 머지 충돌 해결, 작은 수정은 새 head 에서 검증자 하나를 받고, 문구만 바뀌면 아무것도 받지 않는다. 전체 스웜은 swarm 스킬대로 돈다. 관문 레인 하나. PR 의 **검증, 실사용.** 블록의 실사용 레인 열 개. **검증, 성능.** 블록의 성능 레인 하나. 각자 초점이 다른 감사 레인 둘 이상이 diff 와 영수증을 읽고 PR 본문을 믿지 않는다. 루트는 판정 전에 머지 준비 보고의 영수증을 감사한다.
- [ ] 지적마다 실행 플레이북의 막는 규칙으로 판단한다. 막는 것이 없으면 판정이 깨끗하다. `trunk 대비 회귀 레인` 표시가 있는 레인의 trunk 동작 실패는 trunk 에 기록하고 PR 을 막지 않는다. 새 head 는 새 판정을 받는다. mode 스킬의 `playbooks/shipping.md` 의 patch-id 규칙으로 유지되는 결과만 예외다.
- [ ] <실행 플레이북의 머지 또는 넘김 규칙과 `playbooks/shipping.md` 의 patch-id 규칙.>
````
