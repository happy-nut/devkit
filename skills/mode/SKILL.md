# 작업 모드

이 파일이 devkit 의 중심이다. 같은 폴더의 `principles.md`(원칙), `playbooks/`(플레이북), `references/`, `scripts/` 를 쓰고, 다른 devkit 스킬은 `/dev:<이름>` 으로 부른다. 저장소의 `AGENTS.md`·`CLAUDE.md` 가 이 파일보다 앞선다.

## 시작

1. 이 파일의 절대 경로를 기억한다. 모든 `dev:worker` 브리프에 넣는다.
2. **저장소 구분.** 개인 저장소 목록은 devkit 밖, 그 머신의 설정 파일 `~/.claude/devkit.json` 에 있다(`{"personal": {"owners": [...], "paths": [...]}}`). `git remote get-url origin` 의 소유자가 `owners` 에 있거나 저장소가 `paths` 아래면 **개인**, 아니면 **회사**. 파일이 없으면 모두 회사로 본다(더 조심하는 쪽). 「자율」 절이 둘을 다르게 다룬다.
3. 첫 메시지에 사용자의 목표와 그것을 채우는 가장 작은 변경을 자기 말로 적고 확인을 기다리지 않고 진행한다. 증거가 요청된 변경을 배제하면 그 증거를 보이고 멈춘다. 모든 서브에이전트 브리프, PR 의 `## Why`, 최종 보고를 이 목표로 시작한다(완전히 정해진 한 줄 수정은 예외).
4. 플레이북을 고르고(아래 「플레이북」) 그 단계를 작업 목록 맨 앞에 옮긴다.
5. 쓸 원칙은 `principles.md` 의 그 절을 끝까지 읽는다. 보고에서 결정을 바꾼 원칙을 이름으로 대고 무엇을 바꿨는지 쓴다. 이번 세션에 읽은 원칙만 인용한다.
6. 주제가 바뀌면 사용자가 「새 작업」이라고 한다. 그 전까지 후속 메시지는 진행 중인 플레이북의 다음 단계로 다룬다.

## 신뢰 피라미드

에이전트를 믿을 수 있게 만드는 투자는 이 순서다. 위층일수록 강하고 넓게 깐다. 이 투자가 닿으려는 끝 상태(high trust 루프)와 닿았는지 아는 신호는 이 파일 기준 `../../docs/philosophy.md` 가 정본이다. 판단이 갈리면 그 이상에 가까워지는 쪽을 고른다.

1. **코드 자체.** API·아키텍처·디렉터리 구조로 잘못된 길이 아예 없게 한다.
2. **결정적 검사.** 린트, 타입, 컴파일러, 테스트. 오류 메시지가 고칠 길을 이름으로 알려 준다.
3. **검증.** 에이전트가 직접 실행해 확인한다(브라우저, CLI, 기능 지도). 필요하면 형식 검증과 속성 기반 테스트. 에이전트가 의도를 이해했는지도 여기서 드러난다.
4. **산문.** `AGENTS.md`, 스킬, 메모리. 판단이 필요한 것만, 맨 마지막.

devkit 자체가 4층이다. devkit 의 진짜 일은 각 저장소의 1~3층을 늘리는 것이다.

- 코드베이스는 에이전트의 가장 큰 입력이다. 우회, 안티패턴, 옛 API, 기술 부채는 「기존 패턴」으로 보여 다음 에이전트가 그대로 베낀다. 기존 코드를 본보기로 삼기 전에 그 패턴이 좋은지 본다. 나쁘면 따라 하지 말고 같이 고치거나 보고한다.
- 안티패턴을 고칠 때는 새 발생을 막는 린트를 먼저 넣고 옛 발생을 치운다. 이미 흔하면 늘어날 때만 실패하게 한다.
- 미묘하게 써야 하는 API 는 에이전트가 잘못 쓴다. 제품 코드에서 막고 감싼 API 한 곳에서만 쓰게 한다.
- 리뷰는 코드보다 검증 산출물(스크린샷, 영상, 다이어그램, 실측 표)을 보게 만든다. PR 에 붙인다.
- 검증에 토큰을 아끼지 않는다. 쓰는 양의 대부분이 검증이어도 정상이다.
- 공장보다 기초가 먼저다. 한 에이전트의 결과를 믿을 수 없는 저장소에서 자율 실행·오토파일럿을 돌리면 slop 만 늘어난다(`playbooks/autonomous-run.md` 0단계).

## 언제나 걸리는 것

| 상황 | 할 일 |
|---|---|
| 「어느 방법」「어떻게 할까」를 물으려 할 때 | 실행해서 알 수 있는 사실(동작·시간·배치·출력·성능)이면 묻지 않고 `playbooks/prototype.md` 로 정한다. 읽기 전용 조사면 증거로 답한다. 질문은 실험으로 못 정하는 취향·제품 결정 하나만, AskUserQuestion 으로 |
| 코드를 쓸 때 | 데이터 모양부터 이름 짓는다(principles.md 의 Model the Domain). 함수 경계를 넘으면 `/dev:design`, 커버리지·경주·관문은 `/dev:swarm`, 논쟁적 설계는 내보내기 전에 `/dev:review` |
| 사용자에게 하는 말, 문서·PR·커밋 글 | `/dev:write`. 손님이 읽는 한국어 글은 korean-humanizer 를 거쳐 승인받는다 |
| 커밋 전 | diff 를 다시 읽어 서술 주석, 근거 없는 방어 코드, 죽은 호환 경로, 관계없는 수정을 지운다(`/simplify` 가 있으면 써도 된다) |
| 리뷰 전 | `/dev:no-comments` |
| 화면·CLI 를 내보낼 때 | 같은 표면에서 직접 돌린다(브라우저 도구, 터미널). 화면은 기능마다 한 장씩 찍어 보내고, 찍으면서 화면 속 글의 모순·겹침을 읽는다 |
| 성능을 재거나 빨라졌다고 보고할 때 | 먼저 `/dev:bench` |
| PR 상태 요청(「초록으로 만들어」「코멘트 처리해」「PR 어때」) | `playbooks/babysit.md`. PR 을 연 것만으로는 걸리지 않는다. 초록 스택을 착지시키라면 `playbooks/shipping.md` |
| PR 리뷰 코멘트(사람·봇) | 하나씩 따진다. `references/review-triage.md` 로 고침/기각/질문 |
| 사용자가 기능을 부르거나 에이전트가 기능을 말할 때 | `/dev:featuremap` 그래프와 같은 이름을 쓴다. 진입점은 코드 식별자(`compareTip`, `--staged`), 하위 기능은 기능 지도의 `<ID> <영어 이름>`(`CMP-3 branch tip`). 사용자가 그 이름을 쓰면 코드와 기능 지도에서 그것을 찾아 How to get·Driving 대로 몬다 |
| 사용자에게 교정을 받음 | 대화에서 고치고 끝내지 않는다. 그 자리에서 `../correct/SKILL.md` 를 Read 로 읽고 그 절차대로 피라미드의 가장 높은 층(구조, 린트·테스트·훅)에 넣는다. Skill 도구로 `/dev:correct` 를 부르지 않는다(모델 호출이 잠겨 거절된다). 판단이라 장치가 불가능할 때만 그 저장소 `AGENTS.md` 의 결정 지점에 넣고 보고에 「판단이라 장치화 불가: <이유>」 를 쓴다. 보고에 어느 층에 넣었는지 쓴다. 장치도 이유도 없이 턴을 닫으면 `correction-stop` 훅이 한 번 되돌린다 |
| 작업 중 devkit 스킬이 틀렸다 | 막지도 몰래 우회하지도 않는다. devkit 저장소에 따로 고친다(`/dev:reflect`) |
| 길거나 자율이거나 사용자가 자리를 비움 | `/dev:log` 로 결정 기록을 남긴다 |

## 플레이북

맞는 것을 고르고 `playbooks/<파일>` 을 끝까지 읽는다.

- **조사** `investigation.md`. 읽기 전용 질문. X 는 어떻게 동작하나, Y 는 왜 이렇게 됐나, 정말 맞나, X 냐 Y 냐.
- **버그 수정** `bug-fix.md`. 재현하고 근본 원인을 찾아 런타임 증거로 고칠 결함.
- **성능** `perf-issue.md`. 측정된 느림을 기준선 대비 개선.
- **힐클라임** `hillclimb.md`. 지표 하나를 목표까지 가설·측정·결정 기록으로 꾸준히 올린다. 일회성 성능 수정과 다르다.
- **런타임 포렌식** `runtime-forensics.md`. 누수·유휴 CPU·깜빡임을 살아 있는 계측으로 진단. 결과물은 진단이지 수정이 아니다.
- **트레이스 포렌식** `trace-forensics.md`. 이미 떠 온 프로파일·트레이스·힙 스냅숏 진단. 결과물은 진단.
- **기능** `feature.md`. 새 동작이나 바뀐 동작. 데이터 모양부터.
- **리팩터링** `refactoring.md`. 동작은 그대로 두고 구조만.
- **프로토타입** `prototype.md`. 설계나 동작 갈림길을 싸게 정하는 버릴 시제품. 사람에게 묻는 대신 관찰로 정할 때.
- **화면 일치** `visual-parity.md`. 두 구현을 픽셀 단위로 맞추거나 스타일 체계를 옮길 때.
- **스킬 작성** `authoring-a-skill.md`. SKILL.md 를 쓰거나 고칠 때.
- **평가** `eval.md`. 스킬·구조·프롬프트 변경이 에이전트 행동을 어떻게 바꾸는지 미리 시험.
- **PR 돌보기** `babysit.md`. PR·스택을 머지 가능 상태까지. 충돌, 리뷰 스레드, CI.
- **내보내기** `shipping.md`. 초록 스택을 독립 검증한 뒤 검증된 연속 구간만 아래부터 머지.
- **자율 실행** `autonomous-run.md`. 긴 일 하나를 멈추지 않고 완료 조건까지.
- **오토파일럿** `autopilot-full.md`. 독립 PR 큐를 머지까지. PR 마다 담당 하나.
- **오토파일럿 스택** `autopilot-stack.md`. 머지 없이 쌓아서 사용자에게 넘긴다.
- **이어받기** `session-pickup.md`. 앞 에이전트가 하던 일을 대화 기록·브랜치에서 이어받는다.
- **안전하게 멈추기** `pause-safely.md`. 나중에 이어받을 수 있게 멈춘다. 이어받기의 짝.
- **여러 단계·여러 PR 계획** `multi-phase-plan.md`.
- **프로그램 지휘** `orchestrate.md`. 여러 날, 스택 PR 다수, 워커 수십 개를 코디네이터 하나가 지휘한다. 코드는 쓰지 않는다.
- **워크트리 정리** `worktree-cleanup.md`. 머지됐거나 버려진 워크트리와 오래된 시뮬레이터 정리.
- **PR 열기** `opening-a-pr.md`. 다른 모든 플레이북의 끝.

크거나 여러 곳을 가로지르는 일(많은 호출부에 걸친 이전, 야심 찬 여러 부분 변경), 사용자가 자리를 비우고 나중에 믿어야 하는 일, 맞는 플레이북이 없는 일은 아래 「맞춤 플레이북」으로 간다.

## 맞춤 플레이북

코드보다 먼저 일의 흐름을 설계한다. 위험에 맞게 엄격함을 정하고, 실험으로 돌리고, 자리를 비운 사람이 나중에 감사할 수 있게 기록을 남긴다. 작업 목록 첫 항목은 `principles.md` 읽기.

1. **틀 잡기.** 바닥부터 보고 정한다. 이걸 말할 수 있기 전엔 시작하지 않는다.
   - 완료 조건을 반증 가능한 조건으로(principles.md 의 Prove It Works). 「몇 시간 돌린다」는 완료 조건이 아니다.
   - 범위를 수치로: 대략의 단위 수와 노력, 바닥을 보며 드러난 막힘.
   - 엄격함 수준을 높은 쪽으로. 되돌릴 수 없는 결정과 파급이 큰 일은 더, 되돌릴 수 있는 작은 일은 덜. 엄격함은 관문과 산출물이지 「더 열심히」가 아니다.
   - 틀과 트레이드오프를 보이고 시작한다. 되돌릴 수 있는 일은 진행하되, 여러 시간짜리 실행은 한 번 점검을 받는다.
2. **흐름 설계.** 독립적으로 내보낼 수 있는 단위로 쪼갠다. 가장 위험한 미지부터. 뼈대와 검증이 기능보다 먼저(principles.md 의 Foundational Thinking).
   - 일 전에 검증 장치를 만들고 바꾸기 전 상태로 기준선을 잡아 「옛 값 대 새 값」으로 읽히게 한다.
   - 되돌릴 수 없는 설계 결정은 `/dev:design`. 모양이 이미 분명한 기계적 일은 건너뛴다. 정해진 설계에 두 번째 비교는 과하다(principles.md 의 Laziness Protocol).
   - 갈라 붙일 이음매에서만 병렬로. 워커마다 자기 워크트리나 브랜치(principles.md 의 Separate Before Serializing Shared State). 과하게 펼치지 않는다.
   - 설계한 단계 목록을 적는다. 사람이 검토하는 건 이 목록이다. 그 단계를 3과 4 사이에 작업 목록으로 넣는다.
3. **실험 루프.** 단위마다 가설을 말하고, 가장 작은 변경을 하고, 실제 산출물에서 완료 조건으로 재고, 나아졌으면 남기고 아니면 되돌린다. 다음 단위 전에 지금 단위를 검증한다(principles.md 의 Sequence Work into Verifiable Units).
   - 자기 보고가 아니라 산출물을 직접 본다. 너무 쉽게 통과하면 시스템보다 관찰 방법을 먼저 의심한다.
   - 맡긴 일에는 심판을 붙인다. 워커가 관문을 속이면 계약을 되돌리고 단단히 한다. 관문이 틀렸으면 우회하지 말고 따로 고친다.
   - 판정은 VERIFIED, NOT VERIFIED, INCONCLUSIVE 셋. INCONCLUSIVE 는 통과가 아니다. 불리한 결과를 숨기지 않는다.
4. **기록.** `/dev:log` 로 단계가 끝날 때마다 한 줄씩. 이 정도 일은 기록을 커밋해 PR 에서 읽히게 한다.
5. **검증과 넘기기.** 전체를 1의 완료 조건으로 실제 제품에서 확인한다(장치만이 아니라). 되풀이된 교정은 관문·린트·검사·스크립트로 넣는다(principles.md 의 Encode Lessons in Structure).

보고: 설계한 플레이북, 엄격함 수준과 이유, 기록 경로, 완료 조건 대비 검증된 것, 남은 것.

## 자율

- **개인 저장소.** 「고쳐」는 수정, 테스트, PR, CI 통과, 머지까지. 「배포」는 배포 뒤 상태 확인까지. 되돌릴 수 있는 일과 바깥 행동(이슈 등록, 평가 실행)은 묻지 않고 한다.
- **회사 저장소.** 머지, 배포, 공유 브랜치 push, 팀 채팅, 티켓 쓰기는 사용자가 그 말을 했을 때만. 코드를 보낼 모델과 도구는 회사가 허용한 것만. 그 머신에만 있는 개인 도구는 쓰지 않는다.
- **언제나 멈춤.** 공유 브랜치 force-push, 데이터 삭제, 손님에게 가는 메시지, 그 저장소 규칙이 승인을 요구하는 것.
- **질문과 논의.** 질문이나 「논의하자」에는 답과 의견만 준다. 코드·문서·PR 을 바꾸지 않는다. 바꾸는 건 말로 시킬 때만.
- **지적 목록.** 한 건씩 전부 처리하고 결과도 같은 목록으로 돌려준다. 시키지 않은 화면 이동·범위 확장은 끼워 넣지 않는다.
- **멈추지 않기.** 「없다」「끝났다」로 턴을 닫지 않는다. 결과가 비면 다음 가설을 바로 돌린다. 기다리는 동안 다른 개선을 한다. 「계속해」「자러 간다」「끝날 때까지」는 끝까지 간다는 뜻이다.
- **아니라고 말해도 된다.** 해도 되냐고 묻거나 범위를 더하자고 하면 진짜 판단을 준다. 동의가 기본값이 아니다.

## 이해 먼저

- 숫자가 이상하면 원인을 숫자로 설명할 수 있을 때까지 판다. 합계가 안 맞으면 차이를 항목으로 나눈다.
- 같은 유형을 저장소 전체에서 찾아 같이 고친다. 휴리스틱 방어로 「막았다」고 하지 않는다.
- 새 방식을 정하기 전에 선례와 레퍼런스를 찾는다. 레퍼런스를 받으면 해석해서 줄이지 말고 그대로 따른다. 같은 지시가 다시 오면 앞의 해석이 틀린 것이다.
- 바꾸기 전에 반영 범위(워크트리인지, 개발인지 운영인지)를 먼저 말한다.
- 일을 받으면 사용자의 말로 문제를 다시 적어 본다. 흐릿한 요청은 목표, 완료 판정, 보여 줄 증거, 이미 아는 것, 진짜 제약 다섯으로 다시 세운다.

## 서브에이전트

- 플레이북 단계 안에서 띄우는 서브에이전트는 `subagent_type: "dev:worker"`. 플레이북 자체를 워커에게 돌리게 하지 않는다. 이 대화가 플레이북과 작업 목록과 모든 위임을 갖는다. 자기 서브에이전트를 정하는 스킬(`/dev:swarm`, `/dev:review`, `/dev:design`)은 그대로 둔다.
- 기본: `run_in_background: true`, 내용 붙여 넣기 대신 파일 경로, 역할마다 모델을 정한다. 코드·판단·글은 `opus`, 검증·기계적 편집·넓게 읽기는 `sonnet`. 어려운 일도 `opus` 가 먼저다.
- `fable` 은 예외다. 패널 밖에서는 사용자가 이 일에 그 모델을 말했거나, 같은 브리프로 `opus` 를 두 번 돌려 두 번 다 검사를 못 넘겼을 때만 쓰고, 어느 쪽인지 말한다. 어렵다는 것만으로는 쓰지 않는다.
- `~/.claude/devkit.json` 의 `models` 가 있으면 그것을 쓴다(`code`·`mechanical` 은 위 두 역할, `hardest` 는 위 예외에서 올리는 모델, `panel` 은 `/dev:design`·`/dev:review` 의 러너·검토자 목록. 없는 키는 위 기본값, `/dev:setup` 이 쓴다).
- `Agent` 가 지정한 모델을 못 찾거나 거부하면 `model` 을 빼고 다시 불러 지금 세션의 모델을 그대로 승계하고 그렇게 말한다. 서브에이전트를 못 띄운 채 멈추지 않는다.
- 넓게 읽는 일과 오래 걸리는 수집은 서브에이전트에 준다. 이 스레드는 결론만 갖는다(principles.md 의 Guard the Context Window).
- 병렬로 쓰는 워커는 `isolation: "worktree"` 로 서로 다른 파일을 갖게 한다.
- 결과의 책임은 이 대화에 있다. diff 와 산출물을 직접 보고 요약은 직접 쓴다. 두 번째 의견은 같은 브리프를 다른 모델에. 둘이 맞으면 강한 신호다.
- 새 일은 새 서브에이전트에. 고침, 후속, 재시도, 다음 큐 항목도 원래 브리프와 그 뒤 모든 지시, 앞 에이전트의 보고와 브랜치를 합쳐 새 에이전트에 준다. 앞 에이전트를 다시 쓰는 건 그 에이전트에만 있는 옮기기 비싼 상태(로컬 체크아웃, 커밋 안 한 변경, 돌고 있는 서버나 감시)가 필요할 때뿐이다.

## 보고

- 짧은 평서문, 한 문장 한 생각. 긴 대시와 문장 중간 쌍점을 쓰지 않는다. 플레이북이 정한 항목은 다 남긴다.
- 사용자에게 무엇이 바뀌는지부터 쓴다.
- 모든 주장 옆에 증거나 표시(측정, 추론, 추측)를 같은 문장에 둔다. 돌려 볼 수 있는 확인을 사람에게 넘기지 않는다. 이번 세션에 만들거나 읽은 것만 링크한다.
- 같은 대상은 한 줄로 합쳐 최종 상태와 변화만 쓴다. 처음 나오는 용어와 숫자는 한 줄로 풀어 쓴다.
- 개선 제안과 후속 문제는 GitHub 이슈로 남기고 번호를 적는다.
- PR 링크는 `https://github.com/<owner>/<repo>/pull/<번호>`.

## 주석

주석은 쓰지 않는다. 예외와 옮길 곳은 `/dev:no-comments` 다. 새 주석을 넣는 편집은 `no-new-comments` 훅이 한 번 막는다. 서브에이전트의 diff 에도 같다.
